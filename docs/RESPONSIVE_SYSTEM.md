# 2026 이채령 생일카페 웹 반응형 시스템 초안

## 1. 현재 상태 판단

현재 `docs/prod` 구조는 정적 HTML/CSS/JS 기반으로 되어 있고, 메인 화면은 `1600x900` 또는 `540x960` 씬을 통째로 축소/확대하는 방식이다.

이 방식은 아래처럼 강점과 한계가 분명하다.

- 강점: 8-bit 게임 화면 같은 첫 인상을 빠르게 만들기 좋다.
- 강점: 픽셀 아트 자산의 배치가 일정하게 유지된다.
- 한계: 데스크톱/태블릿/모바일에서 같은 정보량을 자연스럽게 재배치하기 어렵다.
- 한계: 디자인 프레임이 늘어날수록 모든 좌표를 다시 잡아야 한다.
- 한계: 공지, 굿즈, 지도, FAQ 같은 문서형 페이지에는 유지보수 효율이 떨어진다.

결론:

`전체 사이트를 고정 씬으로 유지`하는 방식보다, `첫 화면은 컨셉형 씬`, `상세 페이지는 정상적인 반응형 문서 레이아웃`으로 분리하는 하이브리드 구조가 더 적합하다.

## 2. 권장 구조

이번 프로젝트는 행사 소개/공지/위치/굿즈/이벤트 안내가 핵심이라, 프론트엔드 스택을 과하게 키우기보다 현재 정적 구조를 살리되 설계 규칙을 바꾸는 편이 실용적이다.

권장 방식:

- 홈: 8-bit 감성을 강하게 주는 컨셉형 랜딩
- 서브 페이지: 반응형 문서형 레이아웃
- 데이터: 운영시간, 특전, 굿즈, 럭키드로우는 JSON 또는 JS 데이터로 분리
- 스타일: 토큰 기반 CSS + 섹션 단위 컴포넌트 스타일
- 인터랙션: 메뉴 전환, 스크롤 연출, 아코디언, 탭 정도만 최소한으로

즉, `게임 화면처럼 보이는 연출`과 `읽기 쉬운 정보 구조`를 분리한다.

## 3. 디바이스 기준

디자인과 개발은 아래 3개 기준 폭을 공통 언어로 잡는다.

- 모바일: `360px ~ 767px`
- 태블릿: `768px ~ 1199px`
- 데스크톱: `1200px 이상`

기본 작업 원칙:

- 모바일을 최소 기준으로 삼고 위로 확장한다.
- 태블릿은 단순 확대가 아니라 레이아웃 재배치 기준점으로 취급한다.
- 데스크톱은 여백과 비주얼 연출을 강화하되 텍스트 줄 길이를 제한한다.

## 4. 레이아웃 시스템

### 4-1. 페이지 유형을 두 가지로 나눈다

1. `Scene Page`
- 첫 화면 전용
- 픽셀 아트, 로딩 연출, 메인 메뉴, 대표 비주얼 중심
- 필요하면 일부 절대배치를 유지해도 된다

2. `Document Page`
- 공지, 운영시간, 위치, 굿즈, 특전, FAQ, 럭키드로우 안내용
- 일반적인 반응형 흐름 레이아웃 사용
- `section > container > content block` 구조를 기본으로 한다

### 4-2. 공통 컨테이너 규칙

- 모바일 가로 패딩: `16px`
- 태블릿 가로 패딩: `24px`
- 데스크톱 가로 패딩: `32px ~ 48px`
- 본문 최대 폭: `1100px` 내외
- 텍스트 최대 줄 길이: 본문 기준 `60~72자` 정도 유지

### 4-3. 추천 섹션 단위

서브 페이지는 아래 단위로 반복 구성하면 디자이너와 개발자 모두 작업이 쉬워진다.

- hero section
- info grid
- notice list
- goods table / goods card list
- schedule timeline
- map and transit block
- event guide block
- faq accordion
- floating CTA or sticky utility bar

## 5. 디자인 토큰 체계

현재 픽셀 테마는 유지하되, 좌표 중심이 아니라 의미 중심 토큰으로 바꿔야 한다.

필수 토큰 그룹:

- color: 배경, 텍스트, 보조 텍스트, 강조색, 경고색
- spacing: `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64`
- radius: 픽셀 UI 특성에 맞는 테두리 단계
- border: 기본선, 강조선, 패널선
- shadow: 픽셀 패널 그림자, hover 강조
- typography: display, title, body, label, caption
- motion: fade, step, slide, hover press 시간값
- z-index: background, frame, sticky bar, modal

중요:

- 픽셀 감성은 `색상`, `폰트`, `테두리`, `아이콘`, `모션 템포`에서 통일한다.
- 모든 배치를 픽셀 좌표로 고정하지 않는다.

## 6. 디자이너와 협업할 때 필요한 프레임 규칙

디자인 프레임이 이미 있다면, 각 화면을 아래 둘 중 하나로 분류해야 개발이 빨라진다.

- `고정 연출 프레임`: 홈 같은 씬 중심 화면
- `유동 레이아웃 프레임`: 텍스트/표/리스트 중심 화면

디자이너에게 받으면 좋은 정보:

- 각 화면의 모바일/태블릿/데스크톱 버전 존재 여부
- 요소 우선순위: 어떤 요소가 줄어들고 어떤 요소가 유지돼야 하는지
- 이미지 crop 규칙
- 숨김 허용 요소와 줄바꿈 허용 요소
- 섹션 간 간격 규칙
- 버튼/패널/배지 상태 정의

개발 기준으로 다시 정리하면:

- 비주얼은 바뀌어도 구조는 반복되어야 한다.
- 화면마다 완전히 다른 CSS를 만드는 방식은 피한다.

## 7. 파일 구조 권장안

현 구조를 크게 바꾸지 않는 기준이다.

```text
docs/prod/
  index.html
  pages/
    notice.html
    schedule.html
    location.html
    goods.html
    faq.html
  assets/
    css/
      reset.css
      theme.css
      tokens.css
      layout.css
      components.css
      pages.css
      utilities.css
    js/
      app.js
      content.js
      pages/
        notice.js
        schedule.js
        location.js
        goods.js
    img/
  data/
    content.json
    goods.json
    notice.json
```

핵심 원칙:

- `theme.css`: 브랜드/테마 값
- `tokens.css`: spacing, type, radius, z-index 같은 시스템 값
- `layout.css`: container, grid, section, stack
- `components.css`: 버튼, 카드형 패널, 배지, 탭, 아코디언
- `pages.css`: 페이지별 예외 스타일

## 8. 추천 개발 순서

### 1단계. 시스템 먼저

- 브레이크포인트 정의
- 컨테이너/그리드/섹션 규칙 정리
- 타이포 스케일 정의
- 버튼/패널/배지 공통 컴포넌트 확정

### 2단계. 홈 구축

- 컨셉형 메인 랜딩
- 로딩/메뉴/대표 비주얼 정리
- 모바일에서 메뉴 접근성 우선 확인

### 3단계. 정보 페이지 구축

- 운영시간/공지 페이지
- 위치/교통 페이지
- 굿즈/특전 페이지
- 이벤트/FAQ 페이지

### 4단계. 운영 데이터 연결

- 굿즈 리스트
- 특전 조건
- 럭키드로우 규칙
- 문의 채널

### 5단계. 디바이스 QA

- 모바일 세로
- 태블릿 세로/가로
- 데스크톱 일반 해상도
- 긴 텍스트, 품절 상태, 공지 추가 상황 확인

## 9. 지금 시점의 1차 결정안

현재 프로젝트에서는 아래 방향을 추천한다.

1. 기존 `scene` 구조는 메인 페이지 연출에만 제한적으로 사용한다.
2. 상세 안내 페이지는 고정 씬 방식을 쓰지 않고 일반 반응형 레이아웃으로 전환한다.
3. 디자인 시스템부터 만들고, 그 위에 실제 페이지를 얹는다.
4. 운영 데이터는 HTML에 직접 박지 않고 JSON으로 분리한다.

## 10. 다음 구현 시작점

다음 턴에서 바로 해볼 수 있는 작업은 세 가지다.

1. `tokens.css`, `utilities.css`를 추가해서 반응형 기본 시스템부터 만든다.
2. `notice.html` 또는 `schedule.html` 한 페이지를 반응형 샘플 페이지로 먼저 만든다.
3. 현재 메인 홈을 유지하면서 서브 페이지 구조만 먼저 전환한다.

실무적으로는 `2번`이 가장 좋다.

이유:

- 디자이너 프레임을 실제 코드로 옮기는 방식이 바로 검증된다.
- 모바일/태블릿/데스크톱 대응 품질을 가장 빨리 확인할 수 있다.
- 이후 다른 페이지에 복제하기 쉽다.
